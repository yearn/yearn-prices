Drizzle runtime migration

Runtime price reads, writes, backfills, repair queues, guards, and operational scripts now execute through Drizzle. Neon remains the database transport, and Drizzle Kit continues to own migrations.

What changed

  • src/db/orm.ts binds the existing pool or checked-out connection to the shared schema. Adapters are reused per connection.
  • Exact, range, provisional, and price-write operations use typed Drizzle builders. Inventory and backfill writes use the same schema.
  • Atomic queue claims, quarantine operations, maintenance DDL, and bulk data corrections use composed Drizzle SQL with bound parameters. No direct driver query calls remain in src or scripts.
  • Rejection and accepted-price predicates are composable Drizzle SQL expressions.
  • The checksum backfill now keeps each transaction on a dedicated connection and releases that connection in a finally block.

Behavior preserved

Source precedence, exact timestamp matching, repair token casing, immutable finalized prices, provisional updates, rejection filters, lock timeout retries, queue leases, and transaction rollback remain part of the implementation. Price inserts are split into batches of 5,000 rows to stay below PostgreSQL's parameter limit.

The schema change adds a TypeScript source type only; this change does not require a new database migration.

Validation

Application and gateway TypeScript checks pass.

Static inspection confirms no direct driver query calls remain in application and operational script files. Diff whitespace checks pass. Tests and lint were not run under the user's Astra instruction. No live database queries, migrations, or deployments were executed.

Runtime and integration behavior still requires verification in an environment where running tests is authorized. Existing database fixtures now adapt Drizzle query configuration objects and array-mode results. SQL assertions and wrapped-error expectations were updated without executing the tests.
